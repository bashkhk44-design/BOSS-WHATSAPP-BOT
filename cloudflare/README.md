# Cloudflare Workers Migration — Staging Only

Status: **Webhook migration code is now wired for staging; it is not deployed or production-approved.**

All changes in this branch are isolated from `audit-hardening`. Render production, its environment variables, production Telegram webhook/polling state, and the production Neon database have not been changed.

## What has been moved into webhook-capable handlers

### Master bot
- The existing `telegram-master.js` command and callback handlers are retained.
- In `BOSS_WEBHOOK_MODE=true`, the module exports the registered grammY bot and database initializer instead of starting long polling or installing process shutdown hooks.
- The master bot's existing administration, project list, project approvals, AI Analyst, AI Designer, project pipeline, and settings handlers are therefore registered on the webhook bot.

### Client intake bot
- The existing `intake-bot.js` conversation and callback handlers are retained.
- `startIntakeBot(..., { webhook: true })` initializes and returns the bot without starting long polling.
- Approved intake requests still notify the master bot through Telegram.

### Customer bots
- `bot-runtime.js` now exports its existing customer bot factory.
- Worker route `POST /telegram/customer/:id` loads the active bot's encrypted token record from the staging database, decrypts it using the staging encryption key, and runs the existing customer `/start` and `/help` handlers through a webhook.
- This currently ports the customer bot's existing basic handlers, not future custom business logic generated by the AI builder.

### Worker safety and reliability
- `GET /healthz` reports which staging bindings/secrets are configured without exposing their values.
- Routes: `/telegram/master`, `/telegram/intake`, and `/telegram/customer/:id`.
- Each route uses grammY's Cloudflare adapter and Telegram webhook secret-token validation.
- A PostgreSQL table records update IDs by bot and provides duplicate-update protection with retryable failed states.
- The Worker rejects wrong HTTP methods, invalid update IDs, missing configuration, and oversized declared request bodies.
- Wrangler's compatibility date is set to 2026-11-16 for the Node.js compatibility behavior required by the existing CommonJS modules and `pg`.

## Critical staging isolation — do not skip

**Never connect this Worker to the live production bot tokens or the production database.**

Telegram's `setWebhook` changes the update delivery mode for that bot. Do not set a webhook for any bot that is still polling on Render.

Before testing, create:
1. A separate empty Neon staging database/project. Do not use a cloned production database containing production bot tokens or customer records.
2. A new Telegram test bot for the master bot.
3. A new Telegram test bot for client intake.
4. A new random staging-only AES-256 key for `BOTS_ENCRYPTION_KEY`.

Register only newly created test customer bots inside the staging database. Do not register production customer tokens in this staging system.

## Cloudflare bindings and secrets

Create a Cloudflare Hyperdrive binding named `HYPERDRIVE` pointing to the **empty staging Neon database**. The Worker expects `env.HYPERDRIVE.connectionString`; the Hyperdrive binding is intentionally not assigned a fabricated ID in `wrangler.toml`.

Add these values as Cloudflare Worker secrets (not plaintext variables and never in Git):

- `TELEGRAM_BOT_TOKEN` — new staging master bot token.
- `TELEGRAM_ADMIN_ID` — administrator's numeric Telegram ID.
- `MASTER_WEBHOOK_SECRET` — random secret token for the master bot webhook.
- `INTAKE_BOT_TOKEN` — new staging intake bot token.
- `INTAKE_WEBHOOK_SECRET` — random secret token for the intake webhook.
- `CUSTOMER_WEBHOOK_SECRET` — random secret token shared by staging customer bot webhooks.
- `BOTS_ENCRYPTION_KEY` — a new 64-character hexadecimal key for the staging database's bot tokens.
- `GEMINI_API_KEY` — optional, if AI stages are to be tested.

Groq and OpenRouter remain opt-in/optional. Do not copy production secrets automatically.

## Webhook URLs after a staging Worker is deployed

Use only the new staging bot tokens and their matching secret tokens when calling Telegram's `setWebhook` API:

- Master: `https://<worker-host>/telegram/master`
- Intake: `https://<worker-host>/telegram/intake`
- Customer bot ID: `https://<worker-host>/telegram/customer/<database-bot-id>`

Supply the matching `secret_token` parameter to Telegram's `setWebhook` call. Do not do this until the staging Worker and staging database are configured and the health endpoint is checked.

## Checks and remaining validation

- Run `npm test` for the basic Worker routing/preflight tests.
- Run `npm run cloudflare:dev` after the Hyperdrive binding and staging secrets are configured for local/remote development.
- Validate the Worker build with Wrangler before any deployment.
- Test master commands, customer intake from start to approved specification, project notifications, customer bot start/help, AI calls, approval gates, and pipeline failure/retry behavior.
- Confirm that webhook retries do not duplicate projects, AI jobs, approvals, or customer messages.
- Inspect Cloudflare logs and Neon staging records before considering any production cutover.

## Not yet production-approved

1. No Cloudflare deployment has been performed from this branch.
2. No Hyperdrive binding or staging secrets have been configured.
3. No Telegram webhook has been set for any bot.
4. The code has not yet been run in Cloudflare's runtime; bundling/runtime compatibility of the existing AI SDK and all pipeline dependencies still needs validation.
5. The intake and master flows need end-to-end acceptance testing against the separate staging database.
6. Customer bots currently retain only their existing basic `/start` and `/help` behavior; the AI-built per-business runtime is a separate migration stage.
7. Production remains on Render. Do not merge this branch into `audit-hardening`, deploy it as production, rotate production tokens, or change production webhooks until the staging acceptance checklist passes.
